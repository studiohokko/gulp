# コードレビュー（公開・納品前）

**このファイルが判定ルールの正本。** 「レビューして」で使う。コードを理想形にすることではなく、公開・納品後に問題になる箇所を見つける。

結果はワークスペース直下の **`QUALITY_CHECK.md`**。ソースコードは修正しない。

## 使い方

1. **案件のサイト**（テーマ / LP）を Cursor で開く
2. 「**レビューして**」と言う（対象ファイルを指定してもよい）
3. `QUALITY_CHECK.md` を確認する
4. 直してほしい箇所は、チェック後に別途依頼する

GULP テンプレート本体（このリポジトリ）を案件サイトとして見ない。雛形・ダミー文言は仕様。

## AI の手順

1. 対象を決める
   - 指定がなければ、ワークスペース内の表示・動作に関わるソース
   - ファイル / フォルダ指定があればそこだけ
2. 除外してから読む（中を精読しない）
   - `node_modules/` / `vendor/` / `.git/`
   - `package-lock.json` / `*.min.js` / `*.min.css`
   - ビルド成果物の中身（`public/assets/css/style.css`、`public/assets/js/bundle.js` など）。ソース側（`src/`、PHP、HTML）を見る
   - 画像・動画のバイナリそのもの（パス切れ・巨大ファイルの有無は見る）
3. チェック項目に沿って、コードを根拠に指摘する
4. **ソースコードは変更しない**
5. `QUALITY_CHECK.md` を作成または今回の結果で更新する
6. チャットでは件数と最終判定だけ伝え、詳細はファイルへ回す

長くなる場合も、まず実害の大きいものから書いてファイルにまとめる。未確認の範囲があれば「要確認」に書く。

## チェック時のルール

### 1. 推測だけで問題と断定しない

コードから確認できないものは「問題あり」ではなく「要確認（Check）」にする。

### 2. 既存設計を尊重する

現在動いていて明確な問題がない実装を、「別の書き方の方が綺麗」「分けた方が保守しやすい」という理由だけで変更提案しない。FLOCSS / BEM / `rm()` / 論理プロパティなど、このプロジェクトの方針に沿っているものは好みで指摘しない。

プロジェクトで実際に使っている技術だけを対象にする。

### 3. 細かすぎる指摘をしない

原則として指摘不要:

- インデントの統一
- クラス名の分かりやすさ
- コメントの適切さ
- 個人的なコーディングスタイル
- 好みによる記述方法の違い
- 関数やファイルの分割（実害がない場合）

それが直接バグや、更新時に壊れる問題につながる場合だけ指摘する。

### 4. 実害の大きい問題を優先する

「直した方が綺麗」ではなく、次を優先する。

- 表示が壊れる
- 動作しない
- 本番環境でエラーになる
- ユーザーが操作できない
- SEO へ悪影響がある
- セキュリティ上問題がある
- 更新時に壊れる

ARIA は「付けた方が丁寧」だけでは追加提案しない。ネイティブ HTML で足りるなら不要な ARIA を足さない。

## チェック項目

対象は次のうち、表示・動作に関わるファイル。

- HTML
- CSS / SCSS
- JavaScript
- PHP
- WordPress 関連ファイル

### 1. バグ・不具合

- JavaScript / PHP のエラー、Warning / Notice / Fatal につながる可能性
- 存在しない変数・関数・ファイルの参照（`null` / `undefined` 含む）
- HTML タグの閉じ忘れ、不正な入れ子、重複 ID
- リンク切れ、画像・CSS・JS のパス間違い
- 条件分岐・繰り返しのミス
- イベントの多重登録、解除漏れ、特定条件での表示・操作不良
- コンソールエラーにつながるコード
- フォームの入力・送信処理
- WordPress テンプレート上の明らかな問題

### 2. レスポンシブ・表示崩れ

- PC / タブレット / スマートフォンでの表示崩れ
- 固定幅による横スクロール、画像・iframe・表のはみ出し
- `overflow` による意図しない見切れ
- 長いテキスト・英単語・URL が入った場合の崩れ
- 画像の縦横比・サイズ指定、`position: absolute` 等による幅依存の崩れ
- ブレークポイント前後、コンテンツ量の増減で崩れる可能性
- タッチ端末で操作しにくい UI、hover だけに依存した操作

### 3. アクセシビリティ

実際の利用に影響するものを中心に見る。

- 画像の `alt`（装飾に不要な文言が入っていないか含む）
- ボタンとリンクの要素の使い分け
- キーボード操作、フォーカス表示
- フォームの `label`
- 見出し構造（詳細は下の「見出し」）
- モーダル・アコーディオン・メニューなどの開閉が操作不能になっていないか
- JavaScript によって操作不能になるケース
- 色だけで情報を伝えていないか

### 4. SEO・HTML 構造

- `title` / `meta description` / `canonical` / `robots`
- 見出し構造、`h1` の扱い（判定は下の「見出し」に従う）
- 不正な HTML、重複コンテンツ、クロールを妨げる実装
- リンクテキストがリンク先を表しているか
- 構造化データがある場合、内容とマークアップが一致しているか

案件の仕様や WordPress 管理画面側の設定がコードから確認できないものは断定しない。

セマンティックの細部（`div` の多さ、`dl` の有無など）は、アクセシビリティや SEO に実害があるときだけ指摘する。

### 見出し（h1〜h6）

見出しは本の目次と同じで、ページの階層を表す。見るのは **タグの使い方だけ**。文言の変更（言い回し・長さ・キーワードの入れ方）は提案しない。

| タグ | 役割 |
|---|---|
| `h1` | そのページの主題。本のタイトル。1ページに1つが原則 |
| `h2` | 章。セクションのタイトル |
| `h3` | 節。そのセクションの中の小見出し |
| `h4` 以降 | さらに細かいときだけ。SEO のために足す必要はない |

数字が小さいほど階層が上。`<title>` は検索結果やブラウザのタブに出るページ名で、ページ内の `h1` とは別。同じ文言である必要はない。違っていても指摘しない。

階層は飛ばさない。`h2` の次を `h4` にしない。上の階層に戻すのは正しい（`h3` の次のセクションは `h2`）。

指摘には **【必須】【推奨】【確認】** のいずれかを付ける。ファイル名・行と、タグの付け替えだけの修正案を書く。問題がなければ、見出しの節には「見出し：問題なし」とだけ書く。

重要度への対応: 【必須】は 🟠 High、【推奨】は 🟡 Medium、【確認】は ⚪ Check。見出しの指摘は総合結果の件数にも含める。

#### 見出しにすべきもの（h タグを使う）

次をすべて満たすテキストは見出しにする。

- その下に、そのテキストが要約・説明している内容のまとまりが続いている
- そのテキストを目次に載せても違和感がない
- そのテキストを消すと、内容の区切りがわからなくなる

例: セクションタイトル、記事内の小見出し、カード一覧のタイトル（その下に説明文がある場合）、FAQ の質問文（その下に回答がある場合）、フォームのセクション名

#### 見出しにしなくていいもの（h タグを使わない）

次のいずれかに当てはまるテキストは見出しにしない。文字を大きくする目的なら CSS で行う。

- その下に続く内容がない、または 1 行程度しかない
- 装飾・強調が目的（キャッチコピー、英字の飾り文字、注意書き、価格、数値の強調）
- 操作のための文言（ボタン、リンク、タブ、アコーディオンの開閉ラベル）
- ラベル的な短い文言（「NEW」「おすすめ」「Step 1」などのバッジ）
- メタ情報（日付、カテゴリ名、投稿者名、タグ）

#### 判断が分かれやすいケース

修正指示にはしない。【確認】として判断材料を添える。

- セクションの英字サブタイトル（例：「ABOUT」＋「私たちについて」）。意味を持つ日本語を h タグにし、英字は `span` 等で装飾する。または両方をひとつの h タグ内に入れる
- カード一覧の各カードのタイトル。カード内に説明文があれば見出し、タイトルだけのリンク一覧なら不要
- 画像だけで見出しを表している。見出しはテキストが原則。画像のまま見出しにするなら、その `img` の alt に見出しのテキストを入れる
- キャッチコピーがページの唯一の主題になっている。h1 を外すと主題がなくなるので、外す修正は出さない

#### 【必須】必ず修正すべきもの

1. h1 がページ内に存在しない、または主題と無関係な要素（ロゴ等）だけが h1 になっている
2. 見出しレベルを飛ばしている（例：h2 の次に h4）。上のレベルに戻るのは問題なし（h3 → h2、h4 → h2 は OK）
3. 見出しが空（`<h2></h2>` など）、または中身が画像のみで alt が空・未設定
4. 「見出しにしなくていいもの」に h タグを使っている
5. 「見出しにすべきもの」を `<p>` や `<div>` + CSS で見出し風に見せている（例：`<p class="title">`、`<div class="heading">`）

#### 【推奨】改善が望ましいもの

6. h1 がページ内に複数ある（HTML 仕様上は可。ページの主題は1つなので、原則1つ）
7. サイドバー・フッター等、本文と関係ない領域の見出しが `<aside>` / `<footer>` / `<nav>` 等で区切られていない
8. 目次がある場合に、そのリンク先の見出しに id がない。目次がなければ指摘しない

#### 【確認】意図を確認したいもの

9. `<section>` / `<article>` 内に見出しがない
10. 見出し内に `<a>` やアイコンなど、テキスト以外の要素が多い
11. 「判断が分かれやすいケース」に当たり、どちらとも取れるもの

#### WordPress（PHP テンプレート）

WordPress 案件のときだけ。

- 【必須】テーマ全体で h1 が重複していないか（`header.php` のロゴが h1、かつ `single.php` の記事タイトルも h1、など）
- 【確認】トップページ（`front-page.php` / `is_front_page()`）とそれ以外で、h1 の扱いを切り替えているか
- 【必須】`the_title()` や ACF の値を見出しに出すとき、値が空だと空の見出しタグが出ないか
- 【確認】`the_content()` 内（ブロックエディタ）の見出しと、テンプレート側の見出しレベルが衝突していないか（テンプレートの h2 の直後に、本文も h2 から始まる想定か）。本文の中身がコードから見えない場合も【確認】

#### 判定しないこと

- 見出し文言の変更提案（言い回し、長さ、対策キーワードを含めるかどうか）
- `<title>` と `h1` の文言が違うこと
- デザイン上の見出しサイズ（CSS）
- `h4` 以降を SEO のために増やすべきかどうか

### 5. パフォーマンス

細かな最適化ではなく、ユーザー体験へ影響しそうなものを優先する。

- 不必要に大きい画像・動画
- CSS / JavaScript の重複読み込み、不要な外部ライブラリ
- レンダリングを大きく妨げる処理、大量の DOM 操作
- 同じ処理・同じ要素取得の不必要な繰り返し
- WordPress の不要なクエリやループ
- 画像の遅延読み込み漏れ（一覧で明らかに重い場合）

### 6. WordPress / PHP

WordPress 案件のときだけ。使っていなければ省略する。

- テンプレートタグ、フックの使い方
- `WP_Query` / `get_posts` / `query_posts`、`wp_reset_postdata()` の不足
- 出力のエスケープ、入力のサニタイズ、nonce・権限チェック
- `wp_enqueue_style` / `wp_enqueue_script`（依存関係が壊れる直読み込み）
- URL / パスのハードコード、WordPress 関数で取るべき値の直書き
- テーマ変更・URL 変更・管理画面からの更新で壊れる実装
- 非推奨関数、PHP バージョンによる互換性問題

仕様上あえてその実装になっている可能性がある場合は「要確認」にする。翻訳関数の有無など、案件仕様が分からないものは断定しない。

### 7. セキュリティ

Web サイトとして現実的に問題になるものを見る。

- XSS、出力時のエスケープ漏れ
- ユーザー入力のサニタイズ不足、外部入力をそのまま処理している箇所
- nonce 不足
- 機密情報・API キー・パスワード等のコードへの記載
- 公開リポジトリに含めるべきではないファイル

### 8. 納品・公開前チェック

- `console.log` / `var_dump` / `print_r` / デバッグコード
- TODO / FIXME（公開を止めるものかどうか）
- 仮画像、ダミーテキスト、テスト用 URL、localhost、開発環境ドメイン
- 不要なコメントアウト、不要な開発ファイル、公開してはいけないファイル
- 本番環境で動かなくなる可能性のある記述

## 重要度

各指摘には必ず次のいずれかを付ける。

| ラベル | 意味 |
|---|---|
| 🔴 **Critical** | 公開前に必ず修正。サイトが動かない、重大なセキュリティ問題など |
| 🟠 **High** | できる限り公開前に修正。表示・操作・SEO・更新性などに明確な影響 |
| 🟡 **Medium** | 可能なら直した方がよい。特定条件で問題になる可能性 |
| 🔵 **Low** | 必須ではないが、余裕があれば改善できる |
| ⚪ **Check** | コードだけでは判断できず、人間の確認が必要 |

## 出力

チャット上だけで回答せず、ワークスペース直下に `QUALITY_CHECK.md` を作る。既にあれば今回の結果で更新する。

各問題は **タイトル / ファイル / 該当箇所 / 問題 / 影響 / 修正方法**（必要なら修正コード例）。改善コードは必要な範囲だけ。プロジェクト全体の書き換えは Critical のときに限る。該当なしの重要度は「該当なし」と書く。

```markdown
# 品質チェック結果

## 総合結果

- 🔴 Critical：n件
- 🟠 High：n件
- 🟡 Medium：n件
- 🔵 Low：n件
- ⚪ Check：n件

公開を止めるレベルの問題があるかを短く書く。

## 🔴 Critical

## 🟠 High

## 🟡 Medium

## 🔵 Low

## ⚪ 要確認

コードだけでは判断できない項目。「何を確認すればよいか」まで具体的に書く。

## 見出し

見出しルールに沿って書く。各指摘は **【必須】 / 【推奨】 / 【確認】**、ファイル名・行、タグの付け替えだけの修正案。文言の変更は書かない。

問題がなければ次の1行だけ。

見出し：問題なし

## 問題がなかった項目

次のうち、確認できて問題がなかったものを書く。

- バグ・不具合
- レスポンシブ
- アクセシビリティ
- SEO
- パフォーマンス
- WordPress / PHP
- セキュリティ
- 納品前チェック

## 最終判定

次のいずれか。判定理由も短く書く。

**✅ 公開可能**
重大な問題は確認されませんでした。

**⚠️ 修正後に公開推奨**
公開前に修正した方がよい問題があります。

**🚨 公開非推奨**
Critical があり、このままの公開は推奨できません。
```
