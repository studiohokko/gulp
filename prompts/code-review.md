# コードレビュー（公開・納品前）

**このファイルが判定ルールの正本。** 「レビューして」で使う。コードを理想形にすることではなく、公開・納品後に問題になる箇所を見つける。

結果はワークスペース直下の **`QUALITY_CHECK.md`**。ソースコードは修正しない。

## 使い方

1. **案件のサイト**（テーマ / LP）を Cursor で開く
2. 「**レビューして**」と言う（対象ファイルを指定してもよい）
3. `QUALITY_CHECK.md` を確認する
4. 直してほしい箇所は、チェック後に別途依頼する

GULP テンプレート本体（このリポジトリ）を案件サイトとして見ない。雛形・ダミー文言は仕様。

## AI の手順

1. 対象を決める
   - 指定がなければ、ワークスペース内の表示・動作に関わるソース
   - ファイル / フォルダ指定があればそこだけ
2. 除外してから読む（中を精読しない）
   - `node_modules/` / `vendor/` / `.git/`
   - `package-lock.json` / `*.min.js` / `*.min.css`
   - ビルド成果物の中身（`public/assets/css/style.css`、`public/assets/js/bundle.js` など）。ソース側（`src/`、PHP、HTML）を見る
   - 画像・動画のバイナリそのもの（パス切れ・巨大ファイルの有無は見る）
3. チェック項目に沿って、コードを根拠に指摘する
4. **ソースコードは変更しない**
5. `QUALITY_CHECK.md` を作成または今回の結果で更新する
6. チャットでは件数と最終判定だけ伝え、詳細はファイルへ回す

長くなる場合も、まず実害の大きいものから書いてファイルにまとめる。未確認の範囲があれば「要確認」に書く。

## チェック時のルール

### 1. 推測だけで問題と断定しない

コードから確認できないものは「問題あり」ではなく「要確認（Check）」にする。

### 2. 既存設計を尊重する

現在動いていて明確な問題がない実装を、「別の書き方の方が綺麗」「分けた方が保守しやすい」という理由だけで変更提案しない。FLOCSS / BEM / `rm()` / 論理プロパティなど、このプロジェクトの方針に沿っているものは好みで指摘しない。

プロジェクトで実際に使っている技術だけを対象にする。

### 3. 細かすぎる指摘をしない

原則として指摘不要:

- インデントの統一
- クラス名の分かりやすさ
- コメントの適切さ
- 個人的なコーディングスタイル
- 好みによる記述方法の違い
- 関数やファイルの分割（実害がない場合）

それが直接バグや、更新時に壊れる問題につながる場合だけ指摘する。

### 4. 実害の大きい問題を優先する

「直した方が綺麗」ではなく、次を優先する。

- 表示が壊れる
- 動作しない
- 本番環境でエラーになる
- ユーザーが操作できない
- SEO へ悪影響がある
- セキュリティ上問題がある
- 更新時に壊れる

ARIA は「付けた方が丁寧」だけでは追加提案しない。ネイティブ HTML で足りるなら不要な ARIA を足さない。

## チェック項目

対象は次のうち、表示・動作に関わるファイル。

- HTML
- CSS / SCSS
- JavaScript
- PHP
- WordPress 関連ファイル

### 1. バグ・不具合

- JavaScript / PHP のエラー、Warning / Notice / Fatal につながる可能性
- 存在しない変数・関数・ファイルの参照（`null` / `undefined` 含む）
- HTML タグの閉じ忘れ、不正な入れ子、重複 ID
- リンク切れ、画像・CSS・JS のパス間違い
- 条件分岐・繰り返しのミス
- イベントの多重登録、解除漏れ、特定条件での表示・操作不良
- コンソールエラーにつながるコード
- フォームの入力・送信処理
- WordPress テンプレート上の明らかな問題

### 2. レスポンシブ・表示崩れ

- PC / タブレット / スマートフォンでの表示崩れ
- 固定幅による横スクロール、画像・iframe・表のはみ出し
- `overflow` による意図しない見切れ
- 長いテキスト・英単語・URL が入った場合の崩れ
- 画像の縦横比・サイズ指定、`position: absolute` 等による幅依存の崩れ
- ブレークポイント前後、コンテンツ量の増減で崩れる可能性
- タッチ端末で操作しにくい UI、hover だけに依存した操作

### 3. アクセシビリティ

実際の利用に影響するものを中心に見る。

- 画像の `alt`（装飾に不要な文言が入っていないか含む）
- ボタンとリンクの要素の使い分け
- キーボード操作、フォーカス表示
- フォームの `label`
- 見出し構造
- モーダル・アコーディオン・メニューなどの開閉が操作不能になっていないか
- JavaScript によって操作不能になるケース
- 色だけで情報を伝えていないか

### 4. SEO・HTML 構造

- `title` / `meta description` / `canonical` / `robots`
- 見出し構造、`h1` の扱い（見た目だけでレベルを選んでいないか）
- 不正な HTML、重複コンテンツ、クロールを妨げる実装
- リンクテキストがリンク先を表しているか
- 構造化データがある場合、内容とマークアップが一致しているか

案件の仕様や WordPress 管理画面側の設定がコードから確認できないものは断定しない。

セマンティックの細部（`div` の多さ、`dl` の有無など）は、アクセシビリティや SEO に実害があるときだけ指摘する。

### 5. パフォーマンス

細かな最適化ではなく、ユーザー体験へ影響しそうなものを優先する。

- 不必要に大きい画像・動画
- CSS / JavaScript の重複読み込み、不要な外部ライブラリ
- レンダリングを大きく妨げる処理、大量の DOM 操作
- 同じ処理・同じ要素取得の不必要な繰り返し
- WordPress の不要なクエリやループ
- 画像の遅延読み込み漏れ（一覧で明らかに重い場合）

### 6. WordPress / PHP

WordPress 案件のときだけ。使っていなければ省略する。

- テンプレートタグ、フックの使い方
- `WP_Query` / `get_posts` / `query_posts`、`wp_reset_postdata()` の不足
- 出力のエスケープ、入力のサニタイズ、nonce・権限チェック
- `wp_enqueue_style` / `wp_enqueue_script`（依存関係が壊れる直読み込み）
- URL / パスのハードコード、WordPress 関数で取るべき値の直書き
- テーマ変更・URL 変更・管理画面からの更新で壊れる実装
- 非推奨関数、PHP バージョンによる互換性問題

仕様上あえてその実装になっている可能性がある場合は「要確認」にする。翻訳関数の有無など、案件仕様が分からないものは断定しない。

### 7. セキュリティ

Web サイトとして現実的に問題になるものを見る。

- XSS、出力時のエスケープ漏れ
- ユーザー入力のサニタイズ不足、外部入力をそのまま処理している箇所
- nonce 不足
- 機密情報・API キー・パスワード等のコードへの記載
- 公開リポジトリに含めるべきではないファイル

### 8. 納品・公開前チェック

- `console.log` / `var_dump` / `print_r` / デバッグコード
- TODO / FIXME（公開を止めるものかどうか）
- 仮画像、ダミーテキスト、テスト用 URL、localhost、開発環境ドメイン
- 不要なコメントアウト、不要な開発ファイル、公開してはいけないファイル
- 本番環境で動かなくなる可能性のある記述

## 重要度

各指摘には必ず次のいずれかを付ける。

| ラベル | 意味 |
|---|---|
| 🔴 **Critical** | 公開前に必ず修正。サイトが動かない、重大なセキュリティ問題など |
| 🟠 **High** | できる限り公開前に修正。表示・操作・SEO・更新性などに明確な影響 |
| 🟡 **Medium** | 可能なら直した方がよい。特定条件で問題になる可能性 |
| 🔵 **Low** | 必須ではないが、余裕があれば改善できる |
| ⚪ **Check** | コードだけでは判断できず、人間の確認が必要 |

## 出力

チャット上だけで回答せず、ワークスペース直下に `QUALITY_CHECK.md` を作る。既にあれば今回の結果で更新する。

各問題は **タイトル / ファイル / 該当箇所 / 問題 / 影響 / 修正方法**（必要なら修正コード例）。改善コードは必要な範囲だけ。プロジェクト全体の書き換えは Critical のときに限る。該当なしの重要度は「該当なし」と書く。

```markdown
# 品質チェック結果

## 総合結果

- 🔴 Critical：n件
- 🟠 High：n件
- 🟡 Medium：n件
- 🔵 Low：n件
- ⚪ Check：n件

公開を止めるレベルの問題があるかを短く書く。

## 🔴 Critical

## 🟠 High

## 🟡 Medium

## 🔵 Low

## ⚪ 要確認

コードだけでは判断できない項目。「何を確認すればよいか」まで具体的に書く。

## 問題がなかった項目

次のうち、確認できて問題がなかったものを書く。

- バグ・不具合
- レスポンシブ
- アクセシビリティ
- SEO
- パフォーマンス
- WordPress / PHP
- セキュリティ
- 納品前チェック

## 最終判定

次のいずれか。判定理由も短く書く。

**✅ 公開可能**
重大な問題は確認されませんでした。

**⚠️ 修正後に公開推奨**
公開前に修正した方がよい問題があります。

**🚨 公開非推奨**
Critical があり、このままの公開は推奨できません。
```
